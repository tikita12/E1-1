### 슬라이드 4 — 세 가지 핵심 도구
**핵심 한마디:** "터미널·Docker·Git, 이 세 도구를 씁니다."

작업실에는 세 가지 도구가 있습니다.
- **터미널**은 마우스 대신 글자로 명령하는 '대화창'
- **Docker**는 프로그램을 통째로 담는 '도시락통'
- **Git**은 게임의 '세이브 포인트', **GitHub**는 그 세이브 파일을 올려두는 인터넷 보관함입니다.

제 환경은 Windows + PowerShell + Ubuntu(WSL 2) + Docker Desktop + Git 입니다.

### 슬라이드 6 — 절대 경로 vs 상대 경로 🧭
**핵심 한마디:** "주소를 말하는 두 가지 방법입니다."

- **절대 경로**는 '서울시 ○○구 ○○동 123번지'처럼 처음부터 끝까지 다 말하는 주소
- **상대 경로**는 '지금 있는 곳에서 옆 방'처럼 현재 위치 기준으로 말하는 방법

Dockerfile 안에서는 상대 경로 `site/`를, 바인드 마운트에서는 정확한 폴더를 지정해야 해서 절대 경로를 썼습니다.

> 💬 **보충 (질문 들어오면):** 사실 이건 "골라 쓴다"기보다 **각 도구가 그것만 받아줘서**예요.
> - **바인드 마운트**는 절대 경로만 받습니다. (상대 경로를 주면 "그게 어느 폴더인데?" 하고 Docker가 거부)
> - **Dockerfile의 COPY**는 반대로 "프로젝트 폴더 기준"(상대 경로)으로만 찾습니다.
>
> 한 문장으로: **"정확히 콕 집어야 할 땐 절대 경로, 폴더를 옮겨도 따라오게 할 땐 상대 경로."**

### 슬라이드 12 — Dockerfile 2줄 🍕
**핵심 한마디:** "저만의 레시피는 단 두 줄입니다."

- `FROM nginx:alpine` → 이미 잘 만들어진 웹 서버를 바탕으로 시작 (피자 도우 고르기)
- `COPY site/ ...` → 내 웹페이지를 그 안에 넣기 (토핑 올리기)

웹 서버 베이스 이미지에 **정적 콘텐츠만 교체하는 (A) 방식**을 선택했습니다. 간단하고 실수가 적어서요.

> 📖 **줄별 상세 설명 (물어보면 꺼내 쓰기):**
>
> **① `FROM nginx:alpine` — "바닥부터 안 만들고 완성품 위에서 시작"**
> `FROM`은 "이걸 바탕으로 시작하겠다"는 뜻입니다. 웹 서버를 처음부터 만들면 복잡하니, 전 세계가 쓰는 **이미 완성된 웹 서버 NGINX**를 가져다 씁니다. 뒤의 `:alpine`은 그중 **아주 가벼운 버전**이고요. → 🍕 *밀가루부터 반죽하지 않고, 이미 구워진 얇은 도우를 사 와서 시작하는 것.*
>
> **② `COPY site/ /usr/share/nginx/html/` — "내 웹페이지를 NGINX 진열대에 올리기"**
> `COPY A B` = "내 컴퓨터의 A를 → 이미지 안의 B로 복사해 넣어라". 터미널 명령이 아니라 **Dockerfile 안에 적는 레시피 한 줄**입니다.
>
> **③ 왜 하필 `/usr/share/nginx/html/`?**
> NGINX는 손님이 오면 **무조건 이 폴더를 열어서 보여주도록 정해져** 있습니다. NGINX가 태어날 때부터 약속된 "진열대"예요. → 🏪 *가게의 정해진 진열대. 엉뚱한 데 두면 손님(접속자)이 못 봅니다.*
>
> **한 문장 요약:** "이미 완성된 가벼운 웹 서버를 가져와서, 그 서버가 보여주는 자리에 내 웹페이지만 얹었다." 🍱

> ⚠️ **자주 헷갈리는 포인트 (질문 많이 나옴):**
> - **`alpine`은 "nginx의 모델"이 아니라 "가벼운 리눅스 바탕"입니다.** Alpine Linux라는 아주 가벼운 리눅스 위에 nginx를 올린 버전이에요. 발표에선 그냥 **"nginx의 가벼운 버전"**이라고 해도 충분합니다.
> - **`COPY`는 "돌린다(실행)"가 아니라 "넣어둔다(복사)"입니다.** 내 페이지를 nginx가 보는 폴더에 **복사해 넣는 것**이고, 실제로 **돌리는 건 나중에 `docker run`** 할 때예요. → *`COPY`는 "짐 싸기", `docker run`이 "문 열고 영업 시작".*
> - **Dockerfile은 "붕어빵 틀"이 아니라 "레시피(글)"입니다.** 틀(이미지)은 `docker build` 해야 만들어져요. → `Dockerfile(레시피) ─build→ 이미지(틀) ─run→ 컨테이너(붕어빵)`

### 슬라이드 13 — 빌드 → 실행 🏭
**핵심 한마디:** "틀을 만드는 게 build, 찍어 실행하는 게 run입니다."

### 슬라이드 14 — 포트 매핑 🚪➡️🏠
**핵심 한마디:** "현관문 번호를 연결해 주는 규칙입니다."

컨테이너는 독립된 공간이라 밖에서 바로 못 들어갑니다. 컨테이너는 80호에 사는데 내 PC 현관은 8080번. `-p 8080:80`은 **'8080번 현관으로 온 손님을 80호로 안내하라'**는 뜻입니다. **왼쪽이 내 PC, 오른쪽이 컨테이너.** 그래서 같은 80호라도 현관(8080, 8081)만 다르게 하면 두 개를 동시에 운영할 수 있습니다.

> 💬 **보충 — 포트는 "무조건"이 아니라 "밖에서 접속할 때만":**
> `-p`는 `docker run` 할 때 **같이 붙이는 선택 옵션**이고, **밖(내 PC·브라우저)에서 접속해야 하는 컨테이너에만** 필요합니다.
> - **붙이는 경우:** 웹서버처럼 손님을 받아야 하는 것 (`mission-web-container -p 8080:80`, `mission-web-bind -p 8081:80`)
> - **안 붙이는 경우:** 밖에서 접속할 일 없는 것 (`ubuntu-practice`의 `sleep infinity`, `hello-world`, 데이터 보관용 `volume-test`)
>
> 🏠 비유: 포트는 **"손님 받는 가게 현관문"**. 손님 받는 가게(웹서버)는 현관문이 필요하지만, 손님 안 받는 창고(연습용 컨테이너)는 현관문이 필요 없습니다.

### 슬라이드 15 — 접속 증거 🔍
**핵심 한마디:** "실제로 접속되는 걸 눈으로 확인했습니다."

### 슬라이드 16 — 바인드 마운트 🪟
**핵심 한마디:** "내 방과 연결된 창문 같은 겁니다."

> 🔗 **연결 멘트 (15 → 16 넘어올 때 먼저 말하기):**
> "여기까지 보면 웹페이지가 이미 잘 뜹니다. 그런데 한 가지 불편한 점이 있어요. 지금 방식은 파일을 **이미지 안에 복사해 넣는** 방식이라, 글자 하나만 고쳐도 **이미지 재빌드 → 컨테이너 재실행**을 매번 해야 합니다. 오타 하나 고치는 데 명령어가 여러 개죠. 개발하면서 수십 번 고치는데 이러면 너무 번거롭습니다. **그래서 등장하는 것이 바인드 마운트입니다.**"

바인드 마운트는 내 PC 폴더와 컨테이너 폴더를 **창문으로 연결**하는 것입니다. 창문 밖 PC에서 파일을 고치면 컨테이너 안에도 바로 보입니다. 실제로 문구를 `works!`에서 `restored!`로 바꾸고 새로고침만 했더니 **이미지를 다시 안 만들어도** 바로 반영됐습니다. `readonly` 옵션으로 원본을 못 고치게 안전장치도 했습니다.

> 💬 **쉽게 설명 (비유 + 헷갈리는 점):**
> - 바인드 마운트 = **컨테이너 벽에 유리창을 뚫어, 내 PC 폴더를 그대로 공유하는 것.** 단순히 보는 게 아니라 **"같은 폴더 하나"를 PC와 컨테이너가 같이 쓰는 것**이라, 내가 PC에서 고치면 컨테이너도 즉시 반영됩니다.
> - **`COPY`(복사)와의 차이:** COPY는 📄 *사진을 인화해 벽에 붙인 것*(바꿔도 그대로), 바인드 마운트는 🪟 *유리창*(실시간으로 같이 바뀜).
> - ⚠️ **"구글 드라이브 공유 폴더"처럼 실시간 반영된다는 느낌은 맞지만, "클라우드"는 아닙니다.** 인터넷 너머 멀리 올리는 게 아니라 **내 컴퓨터 안에서** 같은 폴더를 공유하는 것 (복사·동기화·인터넷 전부 없음). → 발표에선 **GitHub를 "클라우드 ☁️"**(슬라이드 20)로 쓰므로, 바인드 마운트는 **"유리창/공유 폴더"**로 부르면 안 헷갈립니다.
> - **`readonly`:** 유리창은 뚫되 **컨테이너 쪽은 보기만, 원본은 못 건드리게** 하는 안전장치. (내 PC → 수정 가능 ✏️ / 컨테이너 → 보기만 👀🚫)

### 슬라이드 17 — 틀을 바꾸면 붕어빵도 바뀔까? 🤔
**핵심 한마디:** "이미지와 컨테이너는 분리되어 있습니다."

흥미로운 관찰입니다. 파일을 고치고 이미지를 재빌드해도 **이미 실행 중인 8080 컨테이너는 옛날 문구 그대로**였습니다. 틀을 바꿔도 이미 구운 붕어빵은 안 바뀌는 것과 같죠. 반면 창문으로 연결된 8081은 바로 바뀌었습니다. 이것이 이미지와 컨테이너가 분리되어 있다는 증거입니다.

---

### 슬라이드 18 — 볼륨 🗄️
**핵심 한마디:** "컨테이너가 사라져도 데이터는 남습니다."

컨테이너를 지우면 안의 데이터도 사라집니다. 그래서 중요한 데이터는 Docker가 관리하는 '사물함'인 **볼륨**에 넣습니다. `mission-data` 볼륨에 글을 쓰고, 그 컨테이너를 완전히 삭제한 뒤 새 컨테이너에 같은 사물함을 연결했더니 글이 그대로 남아 있었습니다. 이것이 **데이터 영속성**입니다.

---

### 슬라이드 19 — 창문 vs 사물함 비교
**핵심 한마디:** "용도가 다릅니다. 저는 둘 다 썼습니다."

- **바인드 마운트(창문):** 내 PC 폴더를 직접 연결 → 파일 바로 고치기 좋음 → 웹페이지 수정에 사용
- **볼륨(사물함):** Docker가 관리 → 컨테이너를 바꿔도 안전하게 보관 → 데이터 보관에 사용

---

### 슬라이드 20 — Git & GitHub 💾☁️
**핵심 한마디:** "Git은 세이브, GitHub는 클라우드입니다."

**Git**은 내 컴퓨터에서 작업 기록을 세이브하는 프로그램, **GitHub**는 그 파일을 인터넷에 올려 공유하는 사이트입니다. 사용자 이름·이메일·기본 브랜치 `main`을 설정했고, `git remote -v`로 제 저장소와 연결된 것을 확인했습니다. VS Code 연동도 완료했고, **토큰 같은 민감정보는 문서에 남기지 않았습니다.**

---

### 슬라이드 21 — 트러블슈팅 ① Docker Desktop 창 😱
**핵심 한마디:** "추측이 아니라 로그로 원인을 찾았습니다." ⭐ (가장 강조할 부분)

실습 중 가장 고생한 문제입니다. 명령어로는 Docker가 잘 되는데 **Docker Desktop 화면만 계속 꺼졌습니다.** 재설치도 소용없었습니다. 그래서 오류 로그 파일을 직접 열어봤더니, 화면 프로그램이 설치 폴더를 읽을 **'출입 권한'이 없다**고 적혀 있었습니다. 기존 권한을 백업한 뒤 읽기·실행 권한을 추가했더니 정상적으로 열렸습니다. **추측이 아니라 로그로 원인을 찾은 것이 핵심입니다.**

---

### 슬라이드 22 — 트러블슈팅 ②③ WSL 연결 🔌
**핵심 한마디:** "리눅스와 Docker 연결 문제도 해결했습니다."

- **Ubuntu가 목록에 안 보임** → WSL 기능을 켠 뒤 재시작이 필요했습니다.
- **Ubuntu에서 docker를 못 찾음** → Docker Desktop의 WSL 연동이 꺼져 있어서, 켜고 엔진을 재시작해 해결했습니다.
- 포트가 이미 사용 중일 때 확인하는 방법도 미리 정리해 뒀습니다.

---

### 슬라이드 23 — 보너스 ① Docker Compose 📝
**핵심 한마디:** "긴 명령을 '주문서 한 장'에 적어두고 한 줄로 실행합니다."

여기서부터 보너스 과제입니다. 지금까지는 `docker run` 명령을 매번 길게 입력했는데, **Docker Compose**를 쓰면 그 설정을 `compose.yaml` 파일 한 장에 적어두고 **`docker compose up -d` 한 번**으로 실행할 수 있습니다. 매번 말로 주문하는 대신 **주문서를 적어두는 것**과 같아요. 저는 현재 폴더의 Dockerfile을 빌드하고 **8082 포트**로 연결하도록 적었습니다 (기존 8080·8081과 안 겹치게).

---

### 슬라이드 24 — 보너스 ② 멀티 컨테이너 🔗
**핵심 한마디:** "컨테이너 여러 개를 한 번에, 서로 '이름'으로 통신합니다."

Compose로 웹 서버(`web`)와 통신 확인용 보조 컨테이너(`helper`)를 함께 띄웠습니다. 핵심은 **helper에서 web에 접속할 때 IP 주소가 아니라 서비스 이름 `web`만으로** 찾을 수 있다는 점이에요. Compose가 둘을 **같은 네트워크**에 넣어주기 때문입니다. **같은 건물에서 이름만 부르면 찾아지는 것**과 같죠. 끝나고 `docker compose down`으로 두 컨테이너와 네트워크를 **한 번에 정리**했습니다.

---

### 슬라이드 25 — 보너스 ③ 환경 변수 🎛️
**핵심 한마디:** "코드는 그대로, 설정만 바깥에서 바꿔 끼웁니다."

환경 변수는 프로그램 **바깥에서 설정값을 주입**하는 방법입니다. `APP_MODE`를 `practice`로 지정하고 NGINX가 응답 헤더에 표시하게 했더니, `curl` 확인 시 **`X-App-Mode: practice`** 헤더가 실제로 들어 있었습니다. **같은 기계에서 다이얼만 바꾸는 것**과 비슷해요. 포트는 8084를 썼습니다.

---

### 슬라이드 26 — 보너스 ④ GitHub SSH 🔑
**핵심 한마디:** "비밀번호 대신 '열쇠 한 쌍'으로 인증합니다."

GitHub에 올릴 때 비밀번호·토큰 대신 **SSH 열쇠 한 쌍**으로 인증했습니다. **공개 키(자물쇠)**는 GitHub에 등록하고, **개인 키(열쇠)**는 나만 보관해요. ED25519 방식으로 키를 만들고 **공개 키만** 등록했으며, 개인 키는 저장소에 **절대 올리지 않았습니다.** `ssh -T git@github.com`으로 확인하니 "Hi tikita12! ... successfully authenticated" 성공 메시지가 나왔습니다.

---

### 슬라이드 27 — 평가 결과 📊
**핵심 한마디:** "6개 통과에서 18개 전 항목 통과로 보완했습니다."

AI 사전평가에서 첫 시도는 6개만 통과했지만, 부족한 부분을 보완해 **두 번째 시도에서 18개 전부 통과**했습니다. ① 실제 명령어와 출력을 함께 기록한 점, ② 개념을 실습 사례와 연결한 점, ③ 트러블슈팅을 로그 기반으로 기록한 점이 좋은 평가를 받았습니다. 보완 제안(스크린샷, 네트워크 모드 비교 등)은 앞으로 더 채울 계획입니다.

**핵심 한마디:** "감사합니다. 질문 받겠습니다."

정리하겠습니다. 이번 미션으로 **터미널로 대화하고, Docker로 어디서나 같은 환경을 만들고, Git으로 기록·공유하는** 개발자의 기본 작업실을 완성했습니다. 무엇보다 **문제가 생겼을 때 추측하지 않고 로그로 원인을 찾는 습관**을 배웠습니다. 들어주셔서 감사합니다. 질문 받겠습니다. 🙋

## ❓ 예상 질문 & 답변

**Q. 이미지랑 컨테이너가 정확히 어떻게 다른가요?**
A. 이미지는 '설계도 겸 틀'이라 변하지 않고, 컨테이너는 그 틀로 '실제 실행 중인 것'입니다. 틀 하나로 컨테이너를 여러 개 만들 수 있습니다. (붕어빵 틀 vs 붕어빵)

**Q. 바인드 마운트랑 볼륨 중 뭘 써야 하나요?**
A. 개발하면서 파일을 자주 고칠 땐 바인드 마운트(창문), 중요한 데이터를 안전하게 보관할 땐 볼륨(사물함)이 좋습니다.

**Q. `-p 8080:80`에서 어느 쪽이 내 PC인가요?**
A. 왼쪽(8080)이 내 PC, 오른쪽(80)이 컨테이너입니다.

**Q. 왜 이미지를 재빌드했는데 화면이 안 바뀌었나요?**
A. 이미 실행 중인 컨테이너는 빌드 시점의 내용을 그대로 갖고 있기 때문입니다. 새 내용을 보려면 컨테이너를 새로 만들어야 합니다.

**Q. Docker Desktop 문제는 어떻게 원인을 찾았나요?**
A. 재설치 같은 추측 대신 오류 로그 파일을 직접 열어봤고, '설치 폴더 읽기 권한 없음' 메시지를 보고 권한을 추가해 해결했습니다.

**Q. (보너스) Docker Compose를 왜 쓰나요?**
A. 긴 `docker run` 명령을 매번 치는 대신 `compose.yaml`에 적어두고 한 줄로 실행·정리할 수 있고, 여러 컨테이너를 함께 관리하기도 좋습니다. "주문서 한 장"으로 생각하면 됩니다.

**Q. (보너스) 멀티 컨테이너에서 IP도 모르는데 어떻게 통신하나요?**
A. Compose가 두 컨테이너를 같은 네트워크에 넣어주고, 서비스 이름(`web`)을 주소처럼 쓸 수 있게 해줍니다. 같은 건물에서 이름표로 서로를 찾는 셈입니다.

**Q. (보너스) SSH 개인 키를 저장소에 올려도 되나요?**
A. 절대 안 됩니다. 공개 키(자물쇠)만 GitHub에 등록하고, 개인 키(열쇠)는 내 PC에만 보관해야 합니다. 저도 개인 키는 저장소에 올리지 않았습니다.
